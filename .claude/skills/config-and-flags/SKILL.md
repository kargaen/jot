# Config and flags — the Jot configuration catalog

This is a **catalog**, not a how-to for one feature. It enumerates every
configuration axis in Jot: where each option is defined, its default, whether it
is production or experimental, what guard enforces it, and how to change it.

Read this before touching any env var, preference, capability, or flag. Then
**re-verify** — flags drift, and a stale catalog is worse than none. Re-verify
commands are in *Provenance and maintenance* at the bottom.

Jot's guiding principle (from `README.md`): **defaults matter more than
configuration.** Prefer a strong default over a new knob. Every axis below
exists because a default alone could not express it. Before adding a new one,
first ask whether a better default removes the need.

## 1. Environment variables

Two consumer worlds, kept strictly apart: the **frontend** (Vite bundle, reads
`import.meta.env.VITE_*`) and **scripts / CI / edge functions** (Node/Deno,
read `process.env` / `Deno.env`). The `VITE_` prefix is the boundary — only
`VITE_*` vars are exposed to the browser bundle.

### Frontend (`import.meta.env.VITE_*`)

| Var | Required? | Consumer file | Default / fallback | Guard |
| --- | --- | --- | --- | --- |
| `VITE_SUPABASE_URL` | **Yes** | `src/services/backend/supabase.service.ts` | none | Throws at module import if missing (`"Missing VITE_SUPABASE_URL or VITE_SUPABASE_PUBLISHABLE_KEY in .env"`) |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | **Yes** | `src/services/backend/supabase.service.ts` | none | Same throw-at-import guard as above |
| `VITE_AUTH_REDIRECT_URL` | No | `src/services/backend/auth.service.ts` (`resolveEmailRedirectUrl`) | Falls back to `${origin}/confirmed.html` in web, else `https://kargaen.github.io/jot/confirmed.html` (`DEFAULT_AUTH_REDIRECT_URL`) | None; optional override |
| `VITE_E2E_TEST_EMAIL` | No (e2e only) | `src/test-harness/localDbSmoke.tsx` | none | Only read by the local-DB smoke harness |
| `VITE_E2E_TEST_PASSWORD` | No (e2e only) | `src/test-harness/localDbSmoke.tsx` | none | Only read by the local-DB smoke harness |

Note: `VITE_SUPABASE_ANON_KEY` appears in the ground-truth brief but the code
reads `VITE_SUPABASE_PUBLISHABLE_KEY` (the publishable key **is** the anon key
role in newer Supabase naming). The **throw guard checks only the two required
vars**: `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. This throw
means every context that imports the Supabase service — app, tests, and the
mobile/visual harness — needs at least dummy `VITE_SUPABASE_*` values present in
`.env.local`.

### Scripts / CI / edge (`process.env` / `Deno.env`)

| Var | Required? | Consumers | Where set |
| --- | --- | --- | --- |
| `SUPABASE_URL` | Yes | `scripts/{ci-integration-test,measure-db-latency,rls-ladder}.ts`, both edge functions | GitHub secrets (CI); auto-injected in the Supabase edge runtime; `.env.e2e.local` for local |
| `SUPABASE_ANON_KEY` | Yes (scripts) | `scripts/*` CRUD-as-user paths | GitHub secrets / `.env.e2e.local` |
| `SUPABASE_SERVICE_ROLE_KEY` | Yes (privileged) | `scripts/*` user-lifecycle; both edge functions (`conduit`, `send-space-invite`) | GitHub secrets; auto-injected in edge runtime. **Bypasses RLS — never ship to the browser bundle** |
| `SUPABASE_TEST_USER_NAME` | Yes (CI tests) | `scripts/ci-integration-test.ts`, `rls-ladder.ts` | GitHub secrets |
| `SUPABASE_TEST_USER_PASSWORD` | Yes (CI tests) | same as above | GitHub secrets |

`.env` file map:
- `.env.local` — real (or dummy) frontend `VITE_*` values; git-ignored.
- `.env.e2e.example` — committed placeholder; the working `.env.e2e.local` is
  generated by `npm run db:env:e2e` from `supabase status` and is git-ignored.
- CI reads `SUPABASE_*` and the Android signing secrets from **GitHub
  Actions secrets** — see `build-and-env` for the full setup flow.

## 2. User preferences / runtime settings (localStorage)

All user-facing settings are localStorage-backed. There is **no preferences
store, no server-side settings table** — the design deliberately defers a
central store (see `src/store/README.md`). Each key is read/written by small,
window-safe helper functions so any window (Dashboard, Pulse, Reminder) can
read the same value.

| Key (string literal) | Values | Default | Read/written in |
| --- | --- | --- | --- |
| `jot_nlp_language` (`NLP_LANGUAGE_KEY`) | `"en"` \| `"da"` \| `"auto"` | `"auto"` | `src/services/capture/nlpSettings.service.ts` (`loadNlpLanguageMode` / `saveNlpLanguageMode`) |
| `jot_theme` (`APP_THEME_KEY`) | `"light"` \| `"dark"` \| `"system"` | `"system"` | `src/utils/presentation/theme.ts` |
| `jot_hidden_areas` | JSON `string[]` of area IDs | `[]` | `src/utils/preferences/hiddenAreas.ts` |
| `jot_default_area` (`DEFAULT_AREA_KEY`) | area ID | none (resolved lazily) | `src/services/backend/supabase.service.ts` |
| `jot_remember_me` (`REMEMBER_KEY`) | flag | — | `src/services/backend/auth.service.ts` |
| `jot_auth_snapshot` (`AUTH_SNAPSHOT_KEY`) | JSON session snapshot | — | `src/services/backend/auth.service.ts` |
| Supabase session token (SDK-managed) | — | — | stored via the custom `storage` adapter in `supabase.service.ts` |

Desktop window/reminder state (also localStorage, all `jot_*` literals, defined
where consumed — not central): `jot_compact`, `jot_pin`,
`jot_dashboard_{x,y,width,height,maximized}`, `jot_reminder_enabled`,
`jot_reminder_on_start`, `jot_reminder_time`, `jot_reminder_duration`,
`jot_reminder_opacity`, `jot_reminder_pin`, `jot_reminder_{x,y,width,height}`,
`jot_reminder_snoozed_until`, `jot_last_reminder_date`.

Conventions worth preserving:
- **Default = absence.** `"auto"` (NLP) and `"system"` (theme) are stored by
  *removing* the key, not writing a sentinel. Preserve this when you add a
  preference — the default should be the empty/removed state.
- **NLP language is strict, single-language.** `"en"` and `"da"` are the only
  concrete modes; mixed da/en parsing is intentionally unsupported (a product
  guardrail, not a missing feature). Do not add a "both" mode.
- **Theme** resolves `system` against `prefers-color-scheme` and stamps
  `root.dataset.theme`; the design-token CSS in `src/styles/global.css` reads
  that. Do not hardcode theme colors — see `architecture-contract`.

## 3. Tauri config + permissions (`src-tauri/`)

### `src-tauri/tauri.conf.json` (verify: it is the version SSOT alongside
`package.json` / `Cargo.toml`, synced by `scripts/sync-version.mjs`)

| Field | Value | Notes |
| --- | --- | --- |
| `version` | `1.0.2` | Must match `package.json` + `Cargo.toml`; drift fails `version:check` |
| `identifier` | `com.jot.app` | Bundle identifier; changing it breaks installs |
| `bundle.active` | `true` | Bundling on |
| `bundle.targets` | `"all"` | Windows installer, Android APK, etc. |
| `bundle.createUpdaterArtifacts` | `true` | Produces `latest.json` for the updater |
| `plugins.updater.endpoints` | `https://github.com/kargaen/jot/releases/latest/download/latest.json` | Where the desktop app checks for updates |
| `plugins.updater.pubkey` | (minisign public key) | Verifies update signatures; the private key lives in CI secrets |
| `plugins.deep-link.schemes` | `["jot"]` | `jot://` deep links (desktop + mobile) |
| `app.windows` | `main`, `quick-capture`, `about` | Multi-window desktop; each starts `visible: false` |
| `app.security.csp` | `null` (+ `dangerousDisableAssetCspModification: true`) | CSP intentionally disabled at the Tauri layer |

### Capability / permission model

Two capability files, both scoped to all windows (`"windows": ["*"]`):

| File | Scope | Grants |
| --- | --- | --- |
| `capabilities/defaults.json` (`identifier: "default"`) | **Shared** — all platforms | `core:*` window/webview/event/app permissions, `opener:allow-open-url`, `clipboard-manager:allow-write-text`, `local-storage: true` |
| `capabilities/desktop.json` (`identifier: "desktop"`) | **Desktop only** (`platforms: ["linux","macOS","windows"]`) | `autostart:allow-{enable,disable,is-enabled}` |

Least-privilege is the rule: each `core:window:allow-*` is listed individually
(show, hide, set-focus, center, create, close, set-size, …) rather than a broad
grant. **Add a permission only when a specific command needs it**, and put
desktop-only permissions in `desktop.json`, shared ones in `defaults.json`.

### How native plugins are gated (`src-tauri/src/lib.rs`)

Plugins split into shared vs desktop-only via `#[cfg(desktop)]`:
- **Shared (all platforms)**, registered on the base builder (~line 258):
  `deep_link`, `os`, `opener`, `clipboard_manager`.
- **Desktop-only**, added inside a `#[cfg(desktop)]` block (~line 263):
  `autostart`, `updater`, `process`, `global_shortcut`.

The capability files mirror this: `desktop.json`'s `autostart` permission pairs
with the `#[cfg(desktop)]`-gated `autostart` plugin. If you add a desktop-only
plugin, gate it with `#[cfg(desktop)]` **and** grant its permission in
`desktop.json`, not `defaults.json`.

## 4. Supabase edge-function config (`supabase/config.toml`)

| Function | `enabled` | `verify_jwt` | Auth model |
| --- | --- | --- | --- |
| `[functions.send-space-invite]` | `true` | **`true`** | Supabase gateway verifies a valid user JWT before the function runs |
| `[functions.conduit]` | `true` | **`false`** | No gateway JWT check; the function itself validates a personal API token (`Authorization: Bearer jot_...`) |

**Security implication of `verify_jwt`.** When `verify_jwt = true`, the Supabase
edge gateway rejects any request without a valid Supabase-issued JWT *before*
your code runs — the caller must be a signed-in user. `send-space-invite` relies
on that.

`conduit` sets `verify_jwt = false` **on purpose**: its callers are external
integrations holding a Jot API token, not a Supabase session. Turning off the
gateway check means **the function is fully responsible for its own auth** — it
verifies the `jot_...` token (sha-256 hash compared against the `api_tokens`
table) and then uses the service-role key. Because service-role bypasses RLS,
**every query in conduit must explicitly scope `user_id` to the token owner** —
that scoping *is* the security boundary. Never set `verify_jwt = false` on a
function without an equivalent in-function auth check. See
`architecture-contract` for the Conduit / token model in full.

## 5. How to add a new configuration axis

First decide **which kind of axis** you need — they are not interchangeable:

| You want to… | Use | Where |
| --- | --- | --- |
| Point the app at a backend / inject a secret at build/deploy | **Env var** | `VITE_*` (frontend) or `SUPABASE_*` (scripts/CI/edge) |
| Let a user change behavior at runtime | **Preference** | localStorage key + helper in `src/services/...` or `src/utils/preferences/` |
| Allow a native OS capability | **Tauri permission** | `capabilities/defaults.json` (shared) or `desktop.json` (desktop-only) + `#[cfg(desktop)]` gate in `lib.rs` |
| Toggle an edge function's auth/enablement | **config.toml flag** | `supabase/config.toml` `[functions.*]` |

Checklists:

**New env var**
1. Frontend? It **must** be `VITE_`-prefixed or Vite won't expose it. Read via
   `import.meta.env.VITE_...`.
2. If it is required, add a throw-at-import guard next to the existing one in
   `supabase.service.ts` — fail loud, not silently `undefined`.
3. Add it to `.env.local` (and `.env.e2e.example` if e2e-relevant) and, for CI,
   to GitHub Actions secrets. Coordinate with `build-and-env`.
4. Never expose a service-role or other privileged secret to a `VITE_` var.

**New preference**
1. Add a `*_KEY` constant and `load*/save*` helpers colocated with the feature
   (mirror `nlpSettings.service.ts` / `theme.ts`). Keep it window-safe
   (try/catch around `localStorage`).
2. Make the **default the removed/empty state** where it makes sense.
3. This is service/util-layer work — do not reach into views or controllers in
   the same pass (CLAUDE.md: one layer at a time).

**New Tauri permission**
1. Shared → `defaults.json`; desktop-only → `desktop.json` (and gate the plugin
   with `#[cfg(desktop)]` in `lib.rs`).
2. Grant the **narrowest** permission that unblocks the specific command.

**New edge-function flag**
1. Add a `[functions.<name>]` block with `enabled` and an explicit `verify_jwt`.
2. If `verify_jwt = false`, you own auth inside the function — add the check.

**Production vs experimental labeling.** Mark anything not yet load-bearing
clearly (e.g. the `[experimental]` block already present in `config.toml`). If a
flag is a temporary trial, say so where it's defined so the next reader doesn't
treat it as a supported contract.

**Defaults discipline.** Re-read the top of this file: a strong default usually
beats a new knob. Add the knob only when a default cannot express the need, and
record any *reusable* new convention (a new preference pattern, a new capability
family) in `ARCHITECTURE.md` per CLAUDE.md's "Documenting New Conventions".

## When NOT to use this skill

- You're changing **what a feature does**, not a configurable knob → this skill
  won't help; go to the feature's model/controller/service.
- You're setting up the environment from scratch (installing, first `.env`,
  running the stack) → see the `build-and-env` sibling.
- You're operating a running system (CI runbooks, releases, migrations) → see
  `run-and-operate`.
- You need the RLS / Conduit / token *design* rationale, not the config flag →
  see `architecture-contract`.

Do not duplicate those siblings here; cross-reference them.

```bash
# Frontend env vars actually referenced
grep -rhoE "VITE_[A-Z_]+" src

# Edge-function JWT flags
grep -n verify_jwt supabase/config.toml

# Tauri capability / permission grants

grep -rhoE 'localStorage\.(get|set|remove)Item\([^)]*' src

# Version SSOT + updater config
grep -nE '"version"|endpoints|identifier' src-tauri/tauri.conf.json

# Desktop-only plugin gating
grep -n 'cfg(desktop)' src-tauri/src/lib.rs
```

If a fact here disagrees with the code, the code wins — fix this file in the
same pass.
